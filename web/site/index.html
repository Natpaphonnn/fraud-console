    04.1The problemrank fraud well, then pick the cheapest threshold

    A card issuer scores every transaction. Scores above a threshold go to step-up (manual review or extra authentication such as OTP / 3-D Secure); the rest are approved. Two mistakes cost money in different ways: a good customer stepped up (friction and review effort) and a missed fraud (the amount is lost).

    So the goal has two parts: a model that ranks fraud well, measured by PR-AUC because only 1.70% of transactions are fraud, and a threshold that minimises total expected cost rather than one that maximises an accuracy-style metric.

    04.2Data and its limits20,000 rows · 339 fraud · unspecified provenance
    • Credit Card Fraud Detection 2026 by Udit Jain on Kaggle, released under CC0. It is a public dataset of unspecified provenance: the data card does not say whether rows are real or synthetic, so no result here is a claim about real-world card fraud.
    • 20,000 transactions, 339 of them fraud (1.70%, 95% CI [1.53%, 1.88%]), 24 features. 0 of 26 structural data checks failed.
    • Hints of synthetic generation: channel and device look statistically independent (p = 0.44), and the smallest fraud is 5.14 USD.
    • No customer or card ID and no real timestamp, so no customer-history features, no grouped split and no out-of-time test.
    • The split was locked before any label-based analysis: a development set of 16,000 rows (271 fraud) for 5-fold cross-validation repeated 3 times, and a holdout of 4,000 rows (68 fraud) scored once at the end.
    • The live stream above is a random sample of 2,000 dev rows (34 fraud); it contains no holdout rows.
    04.3Main resultslogistic beat boosting: -0.048 [-0.084, -0.012]

    Final model: logistic regression. A random score has PR-AUC ≈ 0.0169 (the fraud rate); the model reaches about 25× that on cross-validation.

    The holdout agrees with CV within its (wide) intervals. Logistic regression beat the best gradient boosting pipeline (lgbm_tuned, PR-AUC 0.367): boosting minus logistic = -0.048 [-0.084, -0.012]. On this dataset the fraud odds multiply with each extra red flag (×7.6, ×5.7, ×4.9, ×3.2 per flag), the additive log-odds shape a logistic model represents directly. That is a statement about this data, not about fraud models in general.

    The step-up threshold 0.0695 was chosen on dev out-of-fold predictions only (per-repeat optimum 0.0673–0.0834). On CV it catches 69.5% of fraud while stepping up 5.01% of transactions, about 4.3 step-ups per fraud found.

    04.5What didn’t workSMOTE -0.177 · decline tier not distinguishable on holdout

    Every comparison was pre-registered: the simpler option is kept unless the 95% CI of the paired difference (corrected resampled t-test over 15 folds) excludes zero.

    • SMOTE hurt badly (-0.177 [-0.229, -0.125]). SMOTENC fills categorical and boolean features by neighbour majority vote, so synthetic fraud carried red flags only 0.38× as often as real fraud (IP-country mismatch: 31% of real fraud vs 18% of synthetic).
    • Class weights and undersampling were not distinguishable from doing nothing.
    • Calibration: neither sigmoid nor isotonic calibration improved the Brier score.
    • Splines and red-flag interactions (checked later, pre-registered) were not distinguishable from the plain logistic model: -0.016 [-0.041, +0.009] and +0.002 [-0.021, +0.024].

    A third tier (“decline”) did not clearly pay off

    Approve / step-up / decline, with thresholds 0.1166 and 0.4299 chosen on CV, looked cheaper on CV (-104 USD per 1,000 transactions vs two tiers with the same model). On the holdout the difference was -21 USD [-103, +60] per 1,000: the interval includes zero, so the simpler two-tier policy is recommended. Assumes 20% of fraudsters pass step-up and a wrongly declined good customer costs 50 USD. Illustrative assumed costs (not bank data).

    04.7How the evaluation stays honestlocked holdout · pre-registration · tested
    • Holdout locked before any label-based analysis and scored once; a lock file refuses any other pipeline or threshold.
    • All preprocessing and resampling are fitted inside training folds; leakage guards run in the test suite.
    • Comparisons, metrics and decision rules were written down before the results (pre-registration with dated amendments).
    • The in-browser model is the Python pipeline exported as coefficients, one-hot categories and scaler parameters; a test checks that the browser’s score for every transaction on this page matches Python to within 1e-9.
    • Every number on this page is generated from the project’s committed result files; nothing is typed by hand.
